# История ресурсов

## Что сохраняется

Приложение собирает историю ресурсов запущенных процессов: имя приложения,
путь исполняемого файла, CPU, память и доступные GPU%/сетевые показатели.
Это локальная SQLite-база в каталоге данных текущего пользователя. Точный путь
и состояние записи доступны в настройках. Содержимое окон, клавиатура,
посещённые сайты и содержимое сетевых пакетов не собираются.

По умолчанию запись включена, срок хранения — 24 часа. Можно выбрать 1/3/7 дней
или отключить запись. Сохранённые данные остаются доступны для просмотра при
выключенной записи; очистка требует отдельного подтверждения.

История появляется с момента запуска новой версии. Приложение должно работать,
чтобы собирать измерения; скрытие в трей запись не останавливает. После выхода,
паузы или остановки компьютера остаётся разрыв. Программа не восстанавливает
прошлые 12 часов из воздуха.

## Как читать показатели

- CPU выражен в процентах всей вычислительной мощности компьютера, как в текущей
  таблице. Средние значения взвешены по длительности наблюдения.
- Память приложения — сумма памяти его наблюдаемых экземпляров. Пиковые значения
  сохраняются отдельно от средних.
- Несколько экземпляров одного исполняемого файла объединяются; приложения с
  одинаковым именем, но разными доступными путями, различаются. Когда путь
  недоступен, используется имя, поэтому различимость ниже.
- «Время наблюдения» относится к наличию измерений процесса. Оно не показывает
  время взаимодействия человека с приложением.
- CPU-вклад учитывает нагрузку и длительность наблюдения. Краткий пик и
  постоянная небольшая нагрузка имеют разный вклад за весь период.
- `—` и разрывы графика означают отсутствие показателя или измерений. Они не
  подменяются нулями и не интерполируются через остановки сбора.

Сохранённая точка агрегирует 30 секунд: средние и отдельные пики. Это подходящая
детализация для часов анализа; она не является трассировкой каждого события
планировщика ОС. Периоды доступны за 5/15/30 минут и 1/6/12/24 часа с переходом назад/вперёд.
При наведении на график показываются время и доступные значения.
Выделение мышью приближает выбранный интервал (минимум минута); рейтинг и
CSV относятся к этому же диапазону. Начальный период — 15 минут, сброс
возвращает его и слежение за текущим временем. Фоновое обновление сохраняет
последние графики до прихода новой выборки, без замены экрана загрузкой.

## Сетевые оценки

Общий сетевой трафик и трафик отдельных приложений — разные источники данных.
Трафик по приложениям доступен на Linux через NetHogs, на Windows — через отдельный
Windows ETW-сборщик с подтверждением UAC. Включите его в настройках; текущий
статус сбора виден и в истории. История использует изменения
сессионных счётчиков, изолированных по времени старта процесса; повторное чтение
одного NetHogs-кадра не должно увеличивать объём повторно. Неизвестные интервалы,
сбросы счётчиков и паузы не считаются измеренным нулевым трафиком.

Неполное покрытие, короткоживущие процессы и ограничения источников сохраняются.
Windows считает наблюдаемые TCP/UDP-байты; недоступные процессы, ошибки и потеря
ETW-событий не считаются достоверным нулём. Сумма приложений не обязана совпадать
с интерфейсными счётчиками.

Старые интервалы, в которых сбор был выключен, остаются «—». Запуск от
администратора сам по себе не включает запись сети: проверьте настройку сборщика.
Перед сравнением объёмов учитывайте длительность сетевого наблюдения приложения.

## Ограничение ресурсов и надёжность

База обслуживается отдельным потоком. Сборщик и интерфейс не ждут SQL-запросов.
Очередь измерений ограничена; потерянные измерения и ошибки хранения отображаются
в статусе. Срок хранения применяется автоматически. Основной файл базы ограничен
512 МиБ; SQLite также использует служебные файлы журнала.

При штатном выходе сохраняется незавершённая точка. Аварийное завершение может
потерять текущий незафиксированный 30-секундный интервал. Ошибка диска или базы
не должна останавливать текущий монитор процессов. Неизвестная версия схемы
вызывает ошибку, а не перезапись чужих данных.

## Экспорт

Экспорт истории относится к выбранному периоду и загруженному результату.
Он содержит реальные метки времени и явно подписанные показатели; неизвестные
ячейки остаются пустыми. Текстовые имена и пути защищены от интерпретации как
формулы, существующие файлы экспорта не перезаписываются. Экспорт текущей таблицы
процессов остаётся отдельной командой.

## Дополнительные измерения и совместимость

Схема v3 добавляет `extra_metrics`. Миграция выполняется транзакцией кодом
приложения; данные v1/v2 и точная UTC-граница записи сохраняются. В старых
интервалах новые показатели неизвестны, а не равны нулю. Для v1 сохраняется
консервативная граница конца последнего занятого 30-секундного интервала.

Дополнительные метрики имеют независимое время наблюдения, среднее с весом по
длительности и пик. Скорости I/O интегрируются один раз на непрерывный интервал;
их интеграл — наблюдаемые байты. Повторный repaint не записывает и не увеличивает
историю. Старт/пауза, разрыв времени, потеря очереди, смена времени жизни процесса
и неполностью известная группа не дают полного покрытия. Идентичность включает
точный native token создания, если он доступен, кроме PID и UTC-времени старта.
История не переносит данные между процессами при повторном использовании PID.

Linux I/O процесса — `read_bytes/write_bytes` из `/proc/PID/io`; Windows I/O —
transfer counters, которые включают файловые, сетевые и device-операции.
Это не физический трафик накопителя. История устройств хранится отдельно, с
постоянным идентификатором устройства и независимым покрытием; её нельзя
складывать с процессами или использовать для распределения I/O между процессами.
В интерфейсе доступны сводки устройств за выбранный период, без отдельного
многолетнего/неограниченного ряда устройств.

Исторический экспорт дополнительно создаёт `supplementary-summary.csv` для
приложений и устройств и `supplementary-series.csv` для выбранных приложений.
Каждая строка содержит scope, идентификатор, вид метрики, единицу, среднее, пик
и измеренные секунды. `total_bytes` заполнен только для I/O; общий
`integral_value_seconds` имеет единицу исходного значения × секунды и не должен
читаться как байты для памяти или процентов. Неизвестные значения — пустые ячейки,
нулевое покрытие. Все файлы относятся к тому же загруженному запросу и периоду.

Дополнительная таблица увеличивает объём записи пропорционально числу реально
доступных показателей. Срок хранения 1/3/7 дней и предел основной базы 512 МиБ
сохранены; лимит не увеличен ради новых полей. На машинах с большим количеством
процессов предел может достигаться раньше; ошибка записи остаётся явной.


## GPU в Windows и агрегация группы

Windows использует счётчики WDDM `GPU Engine` и `GPU Process Memory` через PDH.
Загрузка процесса — максимум доступных движков по всем адаптерам, а не сумма
процентов параллельных движков. Загрузка группы экземпляров приложения — максимум
GPU% её участников. Например, процессы с 80% и 70% дают группе 80%, а не 150%.
Это показатель наиболее занятого наблюдаемого движка/участника, а не точная
суммарная загрузка устройства всей группой. Если GPU% хотя бы одного участника
неизвестен, покрытие GPU группы за этот интервал отсутствует.

Dedicated и shared GPU memory сохраняются раздельно с независимым покрытием;
память адаптеров и процессов суммируется только при полноте источника. Shared —
системная память для GPU, dedicated — выделенная GPU-память по данным WDDM.
Разделяемые ресурсы могут учитываться у нескольких процессов: сумма не означает
уникальное физическое потребление VRAM. Доступность зависит от WDDM/драйвера,
оборудования и прав счётчиков; отсутствие экземпляра не превращается в ноль.

Существующие записи GPU старых версий сохраняются без пересчёта: прежняя
агрегация могла складывать GPU% экземпляров. Из сохранённого среднего нельзя
восстановить максимум. Такие старые интервалы не следует сравнивать напрямую
с новыми значениями группы; новых ложных нулей или пересчитанных данных нет.

## Покрытие CPU и резидентной памяти

Схема v4 добавляет независимые длительности покрытия CPU и RAM. Время наличия
приложения не считается автоматически временем измерения: у защищённого процесса
может быть известно имя, но отсутствовать CPU или working set. Если хотя бы у
одного экземпляра приложения показатель недоступен, вся группа за этот интервал
не имеет полного показателя. Это независимо для CPU и памяти.

Средние CPU/RAM вычисляются только по соответствующим измеренным секундам;
интервалы с неизвестным значением не уменьшают среднее ложным нулём. Если покрытия
совсем нет, среднее, пик и CPU-вклад неизвестны. CSV оставляет эти ячейки пустыми
и отдельно показывает `cpu_observed_seconds`/`ram_observed_seconds`.

При миграции v1/v2/v3 старым записям сохраняется прежнее покрытие времени наличия:
раньше отсутствие CPU/RAM не было различимо в базе. Старые ложные нули невозможно
надёжно распознать и исправить без исходных измерений. Миграция не делает вид, что
восстановила утраченные данные, не меняет старые значения и не меняет watermark.
Новые наблюдения сохраняют недоступность явно.

RAM процесса — резидентная память/working set, включающая потенциально общие
страницы; сумма приложения не является уникальной физической памятью. Windows
private commit сохраняется отдельно; его нельзя выдавать за working set или
фактическую подкачку. Linux `RssFile+RssShmem` и `VmSwap` также отдельные метрики,
с указанными в интерфейсе ограничениями; `VmSize` не подменяет private commit.

### Lifetime и NetHogs

Сессионные итоги теперь изолированы также по точному native token, включая
повторный PID в одной UTC-секунде. NetHogs сам не даёт этот token, поэтому
его атрибуция остаётся оценкой: молодой процесс показывает `—` до первого
полностью подходящего кадра. Проверяется фактическое начало/время кадра, а не
более поздняя публикация вывода. Неизвестная текущая идентичность не считается
нулём. Windows ETW сохраняет строгую проверку wire FILETIME и точные байты.
